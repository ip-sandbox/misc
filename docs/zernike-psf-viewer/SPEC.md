## 1. 背景と目的

### 1.1 背景

光学系の波面収差は Zernike 多項式の係数列で表現されることが多い。設計・評価の現場では
「この係数を少し変えたら瞳面（波面）と PSF がどう変わるか」を対話的に確かめたい場面が
頻繁にあるが、既存手段は次の理由で使いにくい。

- 商用光学設計ソフトはライセンスが必要で、手元の Windows PC で気軽に開けない。
- Python (numpy/matplotlib, poppy, prysm 等) は簡単だが、**本件の対象環境では Python を
  利用できない前提**である。
- Excel では 2 次元 FFT と画像表示が現実的でない。

### 1.2 目的

Zernike 係数を GUI から入力すると、**瞳面（振幅・位相）と PSF がリアルタイムに表示される**
スタンドアロンツールを、**Python に依存せず Windows 上で単体動作**する形で提供する。

### 1.3 想定ユースケース

| ID | ユースケース |
| --- | --- |
| UC-1 | 特定の Zernike 項（例: 球面収差 0.1λ RMS）を単独で入れ、PSF の崩れ方を確認する |
| UC-2 | 干渉計や設計ソフトから出力された係数列 (CSV) を読み込み、PSF と Strehl 比を確認する |
| UC-3 | 中心遮蔽（副鏡）や矩形瞳など、瞳形状を変えたときの PSF 変化を比較する |
| UC-4 | スライダで係数を動かし、収差の見え方を教育・説明用にデモする |
| UC-5 | 表示中の波面 / PSF を PNG・CSV で書き出し、報告書に貼る |

### 1.4 用語

| 用語 | 意味 |
| --- | --- |
| 瞳面 (pupil plane) | 射出瞳における複素振幅分布。本書では `P(x,y) = A(x,y)·exp(i·2π·W(x,y)/λ)` |
| 波面収差 `W` | 参照球面からの光路差 (OPD)。単位は波長 λ または nm |
| PSF | 点像分布関数。瞳関数のフーリエ変換の強度 |
| λ/D | 回折限界の角度スケール。焦点面上では `λ·F#` |
| `q` | PSF のサンプリング密度 = 1 λ/D あたりの画素数 |
| Strehl 比 | 無収差 PSF ピークに対する収差 PSF ピークの比 |
| RMS / PV | 瞳内での波面の二乗平均平方根 / 最大値−最小値 |

## 2. スコープ

### 2.1 本ツールが行うこと (In scope)

- Zernike 係数の GUI 入力（表・スライダ・直接入力・CSV/JSON 読み書き）
- 瞳面の波面マップ（位相）・振幅マップの表示
- 単色・非コヒーレント・遠方場（フラウンホーファー）近似での PSF 計算と表示
- 評価指標（RMS / PV / Strehl / FWHM / エンサークルドエネルギー）の算出
- MTF（1 次元断面および 2 次元）の表示（オプション機能）
- スルーフォーカス（デフォーカスを振った連続表示）（オプション機能）
- PNG / CSV / JSON へのエクスポート

### 2.2 本ツールが行わないこと (Out of scope)

- 光線追跡・レンズ設計・最適化
- 多波長合成（ポリクロマティック PSF）※ v2 以降の候補
- 視野内の収差分布（フィールド依存）や像シミュレーション（畳み込み）
- 偏光・スカラー近似を超える厳密回折計算
- 近軸外・大 NA でのベクトル回折（高 NA 補正）
- 3D 表示（波面の立体レンダリング）※ v2 以降の候補

## 3. 技術選定

### 3.1 制約条件

| ID | 制約 |
| --- | --- |
| C-1 | Windows 10 (21H2 以降) / Windows 11、x64 で動作すること |
| C-2 | Python ランタイムに依存しないこと |
| C-3 | 管理者権限なしで実行できること（インストーラ不要が望ましい） |
| C-4 | 2D FFT (N=512〜1024) をインタラクティブ速度で回せること |
| C-5 | 2 次元画像をカラーマップ付きで高速描画できること |
| C-6 | GUI の実装技術に HTML/CSS/JS を用いてよい（v0.2 で追加された前提） |

### 3.2 候補一覧

技術選定は本来**独立した 2 つの軸**の組み合わせである。混同すると議論がかみ合わない。

- **軸 1: UI をどこに描くか** — ネイティブウィンドウ / ブラウザ / 埋め込み WebView / 端末
- **軸 2: 数値計算をどこで回すか** — ネイティブプロセス / ブラウザ JS / ブラウザ WASM / GPU

### 3.3 HTML 系 4 形態の詳細

#### H-1: 単一 HTML ファイル（サーバなし）

すべて（HTML/CSS/JS/カラーマップ/WASM）を 1 個の `.html` にインライン化し、
`file://` で直接開く。**配布の観点では本件で最強の選択肢。**

- exe を配らないため **SmartScreen も AV 誤検知も発生しない**。メール添付・共有フォルダ配置・
  社内 Wiki への添付がそのまま配布になる。インストール・ランタイム・管理者権限のいずれも不要。
- ビルド成果物は `esbuild` などで 1 ファイルに束ねるだけ（開発機にのみ Node が要る。配布先には不要）。

`file://` 固有の制約と回避策（**設計時に必ず織り込むこと**）:

| 制約 | 回避策 |
| --- | --- |
| ES モジュール (`<script type="module">` / `import`) は CORS で読めない | 全部インラインの **classic script** として束ねる |
| `fetch()` でローカルファイルを読めない | WASM は base64 で埋め込み `WebAssembly.instantiate(bytes)` で起動。データも埋め込み |
| Web Worker を外部 `.js` から生成できない | `new Worker(URL.createObjectURL(new Blob([src])))` で生成する（**これは `file://` でも動く**）。重い FFT は必ずワーカーへ逃がし UI を固めない |
| `localStorage` が opaque origin で使えないことがある | 設定は JSON のダウンロード / アップロードで永続化（try-catch でフォールバック） |
| ファイル入出力 | 読込は `<input type="file">`、書出しは `<a download>` — いずれも `file://` の Edge/Chrome で動作する |

#### H-2: ローカル HTTP サーバ + 既定ブラウザ（ご提案の構成）

ネイティブの exe が `127.0.0.1` の空きポートで待ち受け、静的 HTML を配信し、
計算 API を提供する。起動時に既定ブラウザを自動で開く。

**この構成が明確に有利になる条件:**

1. **計算はネイティブで、UI は HTML で**やりたい（JS/WASM の性能に不安がある、
   既存の C#/Rust 数値資産を使いたい）
2. **別マシンのブラウザからも開きたい**（計算機は 1 台、閲覧は複数）
3. **同じバイナリを CLI / バッチとしても使いたい**（`--serve` を付けたときだけサーバになる）
4. 大きな配列をサーバ側に置いたまま、ブラウザには表示用の縮小データだけ送りたい

**逆に、単一 PC で完結するだけなら H-3（WebView2）の方が素直**である。H-2 は
ポート・ファイアウォール・プロセス残留・ローカル露出という 4 つの厄介事が付いてくる
（要件と対策は付録 F にまとめた）。

#### H-3: WebView2 埋め込み

OS 内蔵の Edge (Chromium) エンジンをアプリのウィンドウとして使う。
**HTML の UI とネイティブの計算を、HTTP ポートなしで両立できる**のが最大の利点。

| 実装 | 言語 | exe サイズ | 備考 |
| --- | --- | --- | --- |
| Tauri | Rust + Web | 5〜15 MB | 最小。Rust コアを WASM とネイティブの両方に使い回せる |
| C# + `WebView2` コントロール | C# + Web | 自己完結で 70 MB 前後 | `CoreWebView2.PostWebMessageAsJson` / `AddHostObjectToScript` で IPC |
| Photino.NET | C# + Web | 数 MB（framework-dependent） | 薄いラッパ。依存が少ない |
| Wails | Go + Web | 10 MB 前後 | Go を使うなら |

注意点: **WebView2 Runtime（Evergreen）** が必要。Windows 11 と、Edge が入っている
大半の Windows 10 には既に存在するが、**保証はされない**。起動時に有無を判定して、
無い場合は「H-1 の単一 HTML を既定ブラウザで開く」フォールバックを持たせるのが安全。
固定バージョン配布（約 120 MB 同梱）という手もあるが、本件では過剰。

#### H-4 / H-5

- **H-4 Electron**: 引き続き不採用。配布 150 MB 超・起動の遅さ・依存管理が単機能ビューアに見合わない。
  Neutralino.js は軽いが、実体は H-3 と同種でエコシステムが小さく、Tauri を選ぶ方がよい。
- **H-5 HTA**: 追加インストール不要という点だけは魅力だが、レンダリングエンジンが IE11 相当で
  Canvas の性能・ES2015+ の対応・`ArrayBuffer` 周りが厳しい。**採用しない。**

### 3.4 計算をどこで回すか（軸 2）

`N = 1024` の 2D 複素 FFT の演算量はおよそ `2 · N² · log₂N ≈ 1×10⁸ flops`。

| 実行環境 | `N=1024` FFT の見積り | `N=512`（プレビュー） | 備考 |
| --- | --- | --- | --- |
| ネイティブ (C# / Rust / C++) | 20〜50 ms | 5〜12 ms | 余裕あり |
| ブラウザ WASM | 40〜100 ms | 10〜25 ms | Rust/C を `wasm32` にビルド。SIMD 有効化で更に短縮 |
| ブラウザ JS (`Float64Array`) | 100〜300 ms | 25〜70 ms | **プレビュー 512 なら 15〜40 fps は出る見込み** |
| WebGL / WebGPU コンピュート | 数 ms | — | 実装コストが高く、本件では過剰 |

> 上表は演算量からの**見積りであり、実測値ではない**。M1 の最初に
> `N = 512 / 1024 / 2048` のマイクロベンチを実施して確定させること（IT-01 の前提）。

**JS でも要件を満たせる可能性が高い**理由（いずれも実装で効く最適化）:

1. **ゼロ行スキップ** — 瞳は `N` のうち `D_pix` 行しか非ゼロでない（既定 256/1024）。
   行方向 FFT はその 256 行だけ計算すればよく、全体で **約 38% の削減**になる。
2. **基底マップのキャッシュ** — 係数変更時に再計算するのは線形結合と FFT だけ（§4.1）。
3. **二段品質** — ドラッグ中は `N=512`、離した時点で `N=1024`（§8.2）。
4. **Web Worker への隔離** — 計算中も UI が固まらない。最新入力以外は破棄する。

したがって **「まず素の JS/TS で実装し、実測して足りなければ当該カーネルだけ WASM に落とす」**
という順序を推奨する。UI コードは一切変えずに差し替えられる。

### 3.5 描画方式（HTML 系を採る場合）

| 方式 | 内容 | 評価 |
| --- | --- | --- |
| Canvas2D + `ImageData` | JS 側でカラーマップを適用し `putImageData` | 実装が単純。1024² で 10〜30 ms 程度 |
| **WebGL2 テクスチャ + フラグメントシェーダ** | **`R32F` テクスチャに強度を 1 回だけアップロードし、対数 / γ / レンジ / カラーマップをシェーダで適用** | **推奨。表示パラメータの変更に再計算もアップロードも不要で 60 fps。ズーム・パンも GPU 側** |

WebGL2 方式の利点は本件で特に大きい。**「PSF の対数下限スライダを動かす」「カラーマップを変える」
「ズームする」がすべて GPU のユニフォーム変更だけで済み、FFT の再実行が不要**になる。
ネイティブ GUI（案 A）でこれを実現するには自前で同等の仕組みを書く必要がある。

副次的な利点として、断面プロット・MTF グラフ・カラーバー・レイアウト・高 DPI 対応が
HTML/CSS で圧倒的に安く済む（案 A の WinForms では作り込みが必要な部分）。

### 3.6 推奨構成（改訂）

C-6（HTML 可）が加わったことで、**主案を A から H-1 に変更することを推奨する。**

| 位置付け | 案 | 理由 |
| --- | --- | --- |
| **主案** | **H-1: 単一 HTML（計算 = JS/TS + Web Worker、描画 = WebGL2）** | 配布が最も安全かつ簡単（exe なし → SmartScreen/AV/インストール権限の問題が全て消える）。UI 実装コストが最小。性能は二段品質で満たせる見込み |
| **昇格先** | H-1 の計算カーネルのみ WASM 化 | 実測で足りなければ。UI は無変更 |
| **次点** | H-3: Tauri または C# + WebView2 | ネイティブ計算が必須になった場合。**H-1 の UI 資産をそのまま流用でき、移行コストが小さい** |
| **条件付き採用** | H-2: localhost サーバ | §3.3 の 1〜4 のいずれかが要件になった場合。付録 F の要件を必ず満たすこと |
| **代替経路** | E: PowerShell 単一 `.ps1` | 「ブラウザすら使えない / HTML を配れない」場合の逃げ道として仕様は残す |
| **追加 UI** | G: TUI | SSH・リモート運用向け。v2 |
| 不採用 | H-4, H-5, B, C | §3.3 参照 |

**移行のしやすさが H-1 を主案にする決め手**である。H-1 → H-3 → H-2 は
**UI コード（HTML/CSS/JS）をそのまま持ち越せる**一方、案 A（WinForms）を選ぶと
後から HTML に移る際に UI を全部捨てることになる。逆に H-1 から始めれば、
性能や配布形態の要件が変わっても UI 投資は無駄にならない。

> **この変更は Q-9（付録 E）として決定待ちとする。** §9 の UI レイアウトは
> 実装技術に依存しない形で記述してあるため、どちらを選んでも有効である。

### 3.7 決定が覆る条件

| 条件 | 切替先 |
| --- | --- |
| 実測で JS/WASM の性能が §8.2 に届かない | H-3（Tauri / WebView2）または H-2 |
| 計算機と閲覧端末を分けたい / 複数人で同時に見たい | **H-2** |
| 既存の C#・Rust の数値資産を必ず流用したい | H-2 または H-3 |
| CLI・バッチ実行が主たる使い方になった | ネイティブコア（Rust or C#）+ H-2 |
| ブラウザの使用自体が禁止されている環境 | A または E |
| WebView2 Runtime が無い PC が対象に含まれる | H-1（フォールバックとして常に有効） |
| 3D 表示・大規模データのリアルタイム描画が要件に追加された | H-3 + WebGL、または D |
| CUI・リモート環境が主戦場になった | G |

## 4. アーキテクチャ

### 4.1 モジュール分割（ネイティブ構成: 案 A / E / G）

```
ZernikePsf.sln
├─ ZernikePsf.Core/            … GUI 非依存。netstandard2.0 でビルドし PS からも利用可
│   ├─ ZernikeIndex.cs         … OSA/ANSI ⇔ Noll ⇔ Fringe ⇔ (n,m) の相互変換
│   ├─ ZernikePolynomial.cs    … R_n^m と正規化係数、基底マップ生成
│   ├─ PupilBuilder.cs         … 瞳マスク（円形・中心遮蔽・スパイダー・矩形・任意画像）
│   ├─ Fft.cs                  … 1D/2D 複素 FFT（radix-2 Cooley–Tukey, in-place）
│   ├─ PsfCalculator.cs        … 瞳関数 → PSF / OTF / MTF
│   ├─ Metrics.cs              … RMS, PV, Strehl, FWHM, EE
│   └─ Model/                  … OpticalSetup, ZernikeSet, Result（POCO, JSON 直列化対象）
├─ ZernikePsf.Rendering/       … 2D 配列 → Bitmap（カラーマップ・スケーリング）
├─ ZernikePsf.WinForms/        … GUI（主案 A）
├─ ZernikePsf.Tui/             … TUI（案 G, v2）
├─ ZernikePsf.Cli/             … バッチ実行・自動テスト用（係数ファイル → PNG/CSV）
└─ ZernikePsf.Tests/           … 単体テスト（xUnit）
```

### 4.2 モジュール分割（HTML 構成: 案 H-1 / H-3 / H-2）

```
zernike-psf/
```

このインタフェースを保つ限り後から可能である。

### 4.3 計算パイプライン（構成に依らず共通）

```
 [Zernike 係数 c_j]         [光学設定 λ, F#, ε, N, D]
        │                            │
        ▼                            ▼
  基底マップキャッシュ  ────►  波面 W(x,y) = Σ c_j Z_j(x,y)
   （項ごとに 1 回だけ生成）           │
                                      ▼
                     瞳関数 P = A(x,y)·exp(i·2π·W/λ)   ← 瞳マスク A
                                      │
                              zero-pad → N×N
                                      ▼
                                  2D FFT + fftshift
                                      │
                     ┌────────────────┼───────────────┐
                     ▼                ▼               ▼
                 PSF = |F|²      指標 (Strehl 等)   OTF/MTF
                     │
                     ▼
              スケーリング(log/γ) → カラーマップ → Bitmap
```

**性能上の要点:** 基底マップ `Z_j(x,y)`（`N_pupil × N_pupil` の `double[]`）は
係数に依存しないので、瞳設定が変わらない限り再利用する。係数変更時の再計算は
`W = Σ c_j Z_j` の線形結合（O(N²·K)）と FFT のみとなり、スライダのリアルタイム追従が可能。

## 5. 計算仕様

### 5.1 Zernike 多項式

単位円 `0 ≤ ρ ≤ 1`, `0 ≤ θ < 2π` 上で定義する。

```
Z_n^m(ρ,θ) = N_n^m · R_n^|m|(ρ) · cos(mθ)      (m ≥ 0)
Z_n^m(ρ,θ) = N_n^m · R_n^|m|(ρ) · sin(|m|θ)    (m < 0)
```

動径多項式:

```
                (n-|m|)/2       (-1)^s (n-s)!
R_n^|m|(ρ) =      Σ      ──────────────────────────────── ρ^(n-2s)
                 s=0     s! ((n+|m|)/2 - s)! ((n-|m|)/2 - s)!
```

`n - |m|` が奇数のとき `R_n^|m| ≡ 0`。

正規化係数（**RMS 正規化 / OSA・ANSI 標準**）:

```
N_n^m = sqrt( 2(n+1) / (1 + δ_m0) )      δ_m0 は m=0 のとき 1、それ以外 0
```

この正規化では単位円上で `(1/π)∫∫ Z_i Z_j ρ dρ dθ = δ_ij` が成り立ち、
係数 `c_j` はそのまま「その項の RMS 波面誤差」を表す。

**設定で正規化を OFF（`N_n^m = 1`）にできること。** Fringe 系のデータは
非正規化（縁での値 = 係数）で与えられることが多いため。

### 5.2 インデックス方式

3 方式をサポートし、UI から切り替えられる。

| 方式 | 開始 | 変換式 |
| --- | --- | --- |
| OSA / ANSI | j = 0 | `j = (n(n+2) + m) / 2` |
| Noll | j = 1 | n ごとに `\|m\|` 昇順。同一 `\|m\|` では **j が偶数 → cos (m>0)、奇数 → sin (m<0)** |
| Fringe (University of Arizona) | j = 1 | `j = (1 + (n+\|m\|)/2)² − 2\|m\| + ⌊(1 − sgn m)/2⌋` |

対応表は付録 A を参照。**内部表現は常に `(n, m)`** とし、入出力時のみ方式変換する。

### 5.3 波面

```
W(ρ,θ) = Σ_j c_j · Z_j(ρ,θ)        [単位: 波長 λ]
```

係数の入力単位は **λ（波数）** と **nm** を切り替え可能とし、内部は λ 単位で保持する
（nm 入力時は `c[λ] = c[nm] / λ[nm]`）。

ピストン（n=0）とチルト（n=1）は PSF の形状を変えず位置だけを動かすため、
**「ピストン/チルトを除外して指標を計算する」チェックボックス**を設ける（既定 ON）。

### 5.4 瞳関数

```
P(x,y) = A(x,y) · exp( i · 2π · W(x,y) )      (W は λ 単位)
```

`A(x,y)` は瞳の振幅透過率で、次を合成して構成する。

| 要素 | パラメータ |
| --- | --- |
| 円形開口 | 直径 = `D_pix` サンプル |
| 中心遮蔽 | 遮蔽比 `ε = 0.0〜0.9`（`ρ < ε` を 0 にする） |
| スパイダー | 本数 (0/3/4)、幅 [サンプル]、回転角 |
| 矩形／正方 | 幅・高さ [サンプル] |
| ガウシアンアポダイゼーション | `A = exp(−(ρ/w)²)`、`w` 可変 |
| 任意マスク | 8bit グレースケール PNG を読み込み `A = pixel/255` |

> **注意（実装者向け）**: 中心遮蔽や非円形瞳では Zernike の直交性が崩れる。
> したがって **RMS は係数の二乗和 `sqrt(Σ c_j²)` から求めてはならず、
> マスク内の波面マップから数値的に計算する**こと。UI 上でもこの旨を注記する。

### 5.5 PSF

`N × N` の複素配列に瞳関数をゼロパディングして配置し、2D FFT を掛ける。

```
PSF(u,v) = | FFT2( P ) |²        （fftshift して中心を原点に）
```

**サンプリング関係（本ツールの最重要パラメータ）**

- `D_pix` : 瞳直径にあたるサンプル数（既定 256）
- `N` : FFT 配列サイズ、2 のべき乗（既定 1024）
- `q = N / D_pix` : **1 λ/D あたりの PSF 画素数**

このとき焦点面での画素スケールは

```
Δθ = (1/q) · (λ/D)        [rad]
Δx' = (1/q) · λ · F#       [mm など長さ単位]
```

| 条件 | 値 | 備考 |
| --- | --- | --- |
| ナイキスト条件 | `q ≥ 2` | これを下回る設定は UI で警告 |
| 推奨値 | `q = 4` | ピーク位置・FWHM が安定して求まる |
| 既定 | `D_pix = 256, N = 1024` → `q = 4` | |

UI では `N` と `D_pix` を直接入力させるのではなく、
**「瞳サンプル数」と「PSF サンプリング q」を入力し、`N = q · D_pix` を 2 のべき乗に
切り上げて自動決定する**方式とする（`N` の実値と実効 `q` は表示する）。

PSF の正規化は次の 2 方式を切り替え可能とする。

1. **総和正規化**: `Σ PSF = 1`（エンサークルドエネルギー計算用）
2. **無収差ピーク正規化**: 同一瞳マスクの無収差 PSF のピークを 1 とする
   （表示ピーク値がそのまま Strehl 比になる）— 既定

#### 5.5.1 ズーム表示のための MFT（推奨オプション）

FFT でズームしようとすると、**「ズーム倍率を上げる = `q` を上げる = `N` を増やす」**という
関係になり、`±4 λ/D` を細かく見たいだけでも巨大な配列が必要になる（`q=16` なら `N=4096`）。
インタラクティブなズームとは相性が悪い。

これを避けるため、**MFT (Matrix Fourier Transform, Soummer et al. 2007)** を併用する。
瞳配列 `P`（`N_p × N_p`）から、像面の任意の範囲・任意のサンプリングを
2 回の行列積で直接得る方法である。

```
E_img = F_y · P · F_xᵀ

  F_x[k, l] = exp( -i·2π · u_k · x_l )      (N_img × N_p)
  u_k : 像面のサンプル座標 [λ/D 単位]  x_l : 瞳のサンプル座標 [瞳半径単位]
```

| | FFT | MFT |
| --- | --- | --- |
| 計算量 | `O(N² log N)`（`N` は padding 後のサイズ） | `O(N_p²·N_img + N_p·N_img²)` |
| `q`（サンプリング） | `N/N_p` の離散値のみ | **任意の実数値**を直接指定できる |
| 出力範囲 | 常に全視野 | **必要な範囲だけ**計算できる |
| メモリ | `N²` の複素配列が必要 | 瞳と出力のみ |
| 向き | MTF、全視野、エネルギー総和 | **ズーム表示、コア付近の詳細** |

例: `N_p = 256`、表示 `256 × 256` 画素の場合、MFT は約 3.4×10⁷ 回の複素乗算で、
`N = 1024` の FFT（約 1×10⁸ flops）と同等かそれ以下。**しかもズーム倍率を変えても
コストが変わらない**（出力画素数が同じなら同じコスト）。

**実装方針:**

- **既定の表示（`±16 λ/D` 程度）と MTF・エネルギー総和** → FFT 経路
- **ズームイン時（`q` を上げたい / 範囲を狭めたい）** → MFT 経路
- 両経路の結果が一致することを UT-15 で検証する（同一 `q`・同一範囲で相対誤差 < 1e-6）

v1 では FFT 経路のみでも要件は満たせるため、MFT は **S（望ましい）** 扱いとする。
ただし §4.2 のモジュール構成には最初から `mft.ts` の場所を用意しておくこと。

### 5.6 評価指標

| 指標 | 定義 | 備考 |
| --- | --- | --- |
| PV | `max(W) − min(W)`（マスク内） | λ 単位 |
| RMS `σ` | `sqrt( Σ A²(W−W̄)² / Σ A² )` | マスク内。振幅重み付き |
| Strehl（定義値） | `S = abs( Σ A·e^{i2πW} )² / (Σ A)²` | 原点における強度比。厳密 |
| Strehl（実測ピーク比） | `max(PSF_ab) / max(PSF_ideal)` | チルト起因のずれを含まない値。両方表示 |
| Maréchal 近似 | `S ≈ exp(−(2πσ)²)` | `σ` は λ 単位 RMS。`σ ≲ 0.1λ` で有効 |
| FWHM | PSF の半値全幅 | `λ/D` 単位。放射平均から補間で算出 |
| EE(r) | 半径 `r` 内の全エネルギー比 | 半径は `λ/D` 単位 |

### 5.7 OTF / MTF（オプション機能）

```
OTF(f) = FFT2( PSF ) / FFT2( PSF )|_{f=0}
MTF(f) = |OTF(f)|
```

周波数軸は `Δf = q / (N · λ · F#)`。理想瞳のカットオフ `f_c = 1/(λ·F#)` は
配列上でちょうど `D_pix` 画素目にあたる（実装の検算に使える）。

### 5.8 数値仕様

| 項目 | 仕様 |
| --- | --- |
| 実数型 | `double`（倍精度） |
| FFT | radix-2 Cooley–Tukey、in-place、twiddle 係数を事前計算してキャッシュ |
| FFT サイズ | 256 / 512 / 1024 / 2048（2 のべき乗のみ） |
| 角度計算 | `Math.Atan2(y, x)`。`ρ = 0` の点では `θ = 0` |
| 座標 | 画素中心基準。`N` が偶数のとき原点は `N/2` 画素目（fftshift 後） |
| 動径多項式 | 階乗はガンマ関数ではなく整数テーブルで計算（`n ≤ 20` を保証範囲とする） |
| 最大次数 | `n ≤ 10`（OSA j ≤ 65）を必須、`n ≤ 20` を努力目標 |

```json
{
  "schemaVersion": 1,
  "wavelengthNm": 550.0,
  "coefficientUnit": "waves",
  "indexScheme": "OSA",
  "normalized": true,
  "coefficients": [
    { "n": 2, "m": 0,  "value": 0.05 },
    { "n": 4, "m": 0,  "value": 0.10 },
    { "n": 3, "m": 1,  "value": -0.02 }
  ],
  "pupil": {
    "shape": "circular",
    "pupilSamples": 256,
    "obscurationRatio": 0.0,
    "spider": { "count": 0, "widthSamples": 2.0, "rotationDeg": 0.0 },
    "apodization": { "type": "none", "width": 1.0 },
    "maskImagePath": null
  },
  "psf": {
    "samplingQ": 4.0,
    "fftSize": 1024,
    "normalization": "idealPeak"
  },
  "display": {
    "psfScale": "log",
    "psfLogFloorDb": -50.0,
    "psfZoomLambdaOverD": 16.0,
    "wavefrontColormap": "coolwarm",
    "psfColormap": "viridis",
    "excludePistonTilt": true
  }
}
```

- **係数は必ず `(n, m)` で保存する。** インデックス番号で保存すると方式変更時に破綻するため。
- `schemaVersion` が未知の場合は読み込みを中止し、理由をダイアログで表示する。
- 未知キーは無視する（前方互換）。欠落キーは既定値で補う。

### 7.2 係数 CSV

読み込み時は次の 2 形式を自動判別する。ヘッダ行（`#` 始まりまたは非数値行）は無視。

```
# 形式 1: インデックス, 値   （インデックス方式は UI の現在設定に従う）
4,0.05
11,0.10

# 形式 2: n, m, 値           （方式に依存しないため推奨）
2,0,0.05
4,0,0.10
```

区切りはカンマ / タブ / 空白を許容。小数点はピリオドのみ（ロケール非依存で
`InvariantCulture` により解釈）。書き出しは常に形式 2。

### 7.3 マップ CSV

`N` 行 × `N` 列の数値。1 行目に `# key=value` 形式のメタ情報を出力する。

```
# type=wavefront unit=waves size=256 pupilSamples=256
# type=psf unit=normalized size=1024 samplingQ=4 lambdaOverD_perPixel=0.25
```

| 条件 | 目標 |
| --- | --- |
| 係数 1 個変更 → 再表示 (`N=1024`, `D_pix=256`) | **100 ms 以内** |
| スライダドラッグ中 | プレビュー品質（`N=512`）で **30 fps 以上**、離した時点でフル品質に再計算 |
| 起動から入力可能まで | 2 秒以内 |
| `N=2048` でのフル計算 | 1 秒以内 |

計算は UI スレッドから分離し（`Task` + `CancellationToken`）、新しい入力が来たら
実行中の計算をキャンセルして最新値で再実行する（**最新値のみを処理し、中間の入力は捨てる**）。

### 8.3 配布

| 構成 | 成果物 | 配布方法 |
| --- | --- | --- |
| **H-1（主案）** | `ZernikePsfViewer.html` **1 ファイル** | メール添付・共有フォルダ・社内 Wiki に置くだけ。**インストール・実行権限・SmartScreen・AV 例外のいずれも不要**。ダブルクリックで既定ブラウザが開く |
| H-3 | `ZernikePsfViewer.exe`（Tauri で 5〜15 MB） | ZIP 展開して実行。**未署名 exe は SmartScreen 警告の対象**。可能ならコード署名する |
| H-2 | `ZernikePsfViewer.exe`（サーバ兼配信） | 同上。加えて付録 F の要件を満たすこと |
| A / E / G | `.exe` / `.ps1` | §3.2.1 のとおり |

共通事項:

- レジストリを汚さない。アンインストールは**ファイルを消すだけ**で完了すること。
- 設定の永続化:
  - H-1: `localStorage`（`file://` で使えない場合があるため必ず try-catch し、
    失敗時は「設定 JSON をダウンロード / 読み込み」に一本化する）
  - H-2 / H-3 / A: 実行ファイルと同じフォルダの `settings.json`、
    書込不可なら `%LOCALAPPDATA%\ZernikePsfViewer\` にフォールバック
- **H-1 が exe を必要としないことは、本件で最大の配布上の利点**である。
  対象 PC のロックダウンが厳しいほど価値が上がるため、他構成を選ぶ場合でも
  H-1 相当の単一 HTML を**常にビルド成果物として併産する**ことを推奨する。

| --- | --- |

## 12. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| FFT のスケール・シフト規約の取り違え | PSF が微妙にずれ、気付きにくい | UT-07〜UT-09（Airy 半径・チルト移動量）で規約ごと検証する |
| インデックス方式の混同 | 別の収差を表示してしまう | 内部を `(n,m)` に統一。UI に常時 `(n,m)` を併記。UT-03/UT-04 |
| 遮蔽瞳での係数由来 RMS の誤用 | 指標が実態とずれる | RMS は必ずマップから数値計算。UI に注記 |
| 単一 exe のサイズ・AV 誤検知 | 配布時の摩擦 | **H-1 を採れば exe 自体が不要になり、このリスクは消える**。exe を配る構成ではトリム有効化・framework-dependent 版の併産・可能なら署名 |
| JS の計算速度が §8.2 に届かない | 操作がもたつく | M1 で先に実測（§3.4）。不足時はカーネルのみ WASM 化 → それでも不足なら H-3/H-2 へ。**UI コードは無変更で移行できる設計にしておく**（§4.2） |
| `file://` 固有の制約を踏む | H-1 が動かない | §3.3 の表の回避策を設計時に織り込む。Worker は Blob URL 経由、モジュールはインライン化、WASM は base64 埋め込み。IT-06 で実機確認 |
| WebView2 Runtime が無い PC | H-3 が起動しない | 起動時に有無を判定し、無ければ単一 HTML を既定ブラウザで開くフォールバックを持つ |
| WebGL2 が使えない（古い GPU・RDP 経由・GPU 無効化ポリシー） | 画像が出ない | 起動時に `getContext("webgl2")` を試し、失敗したら Canvas2D 経路へ自動フォールバック（IT-07） |
| H-2 のポートがローカルの他プロセスから叩かれる | 意図しない操作・情報取得 | 付録 F の F-3〜F-5（loopback バインド・ワンタイムトークン・Origin 検証）を必須とする |
| H-2 のプロセスがブラウザを閉じても残る | 二重起動・リソース占有 | 付録 F の F-6（ハートビートとアイドルタイムアウト）を必須とする |
| GUI スレッドでの重い計算 | フリーズ | 計算は別スレッド。キャンセル可能。プレビュー品質の二段構え |
| 高次項での階乗オーバーフロー | 誤った多項式 | 整数テーブル + `n ≤ 20` の上限チェック |
| 対象 PC に何も置けない事態 | 配布不能 | 案 E（PowerShell 単一ファイル）を代替経路として維持 |

## 付録 C. 代替案 E（PowerShell）の構成メモ

「対象 PC にビルド成果物すら置けない」場合の逃げ道。単一の `ZernikePsfViewer.ps1` で完結する。

```powershell
# 1) 数値カーネルを C# ソース文字列として埋め込み、初回起動時に JIT コンパイル
Add-Type -TypeDefinition @"
public static class Kernel {
    public static void Fft2(double[] re, double[] im, int n) { /* ... */ }
    public static double[] Wavefront(double[] coeff, int nPupil) { /* ... */ }
}
"@ -ReferencedAssemblies System.Drawing

# 2) GUI は System.Windows.Forms を直接叩く
Add-Type -AssemblyName System.Windows.Forms, System.Drawing
$form = New-Object System.Windows.Forms.Form
# ... DataGridView / TrackBar / PictureBox を配置
```

制約と注意:

- **PowerShell のループで FFT を回してはならない。** 1024² の 2D FFT は
  PowerShell スクリプトのままだと数十秒〜数分かかり、要件を満たさない。
  重い処理は必ず `Add-Type` 側（C#）に置く。
- Windows PowerShell 5.1 前提（OS 標準）。PowerShell 7 では `Add-Type` の
  `-ReferencedAssemblies` 指定が異なるため、両対応するなら分岐が必要。
- 実行ポリシーの回避が必要な場合がある:
  `powershell -ExecutionPolicy Bypass -File ZernikePsfViewer.ps1`
- 機能は FR-01, FR-05, FR-07（円形＋遮蔽のみ）, FR-08, FR-10, FR-13, FR-17 に絞る。
- 主案 A が使える場合は、同じ `ZernikePsf.Core.dll` を
  `Add-Type -Path .\ZernikePsf.Core.dll` で読み込む構成に切り替えられる。

## 付録 D. 代替案 G（TUI）の構成メモ

SSH / リモート・GUI 不可環境向け。`ZernikePsf.Core` を共有し、フロントのみ差し替える。

- 描画: Unicode 半角ブロック `▀` の前景色/背景色を別々に指定し、
  **1 セルで縦 2 画素**を表現する（24bit True Color、Windows Terminal / ConHost v2 対応）。
  非対応端末向けに ASCII 濃淡（` .:-=+*#%@`）へのフォールバックを用意する。
- Sixel 画像表示は Windows Terminal 1.22 以降でのみ利用可能。**必須要件にはしない。**
- レイアウト: 左に係数リスト（↑↓ で項選択、←→ で値増減）、右に瞳面と PSF、下に指標。
- 解像度は端末サイズに合わせてダウンサンプルする（表示用のみ。計算は本来の解像度）。
- ライブラリ: C# なら `Spectre.Console`、Rust なら `ratatui` + `crossterm`。

## 付録 F. 案 H-2（ローカル HTTP サーバ）を採用する場合の要件

localhost サーバ構成は「ネイティブの計算 + ブラウザの UI」を両立できる一方、
**ポート・ファイアウォール・ローカル露出・プロセス寿命**という 4 つの厄介事を持ち込む。
H-2 を採る場合、以下は**すべて必須要件**とする（IT-08 で検証する）。

### F.1 ネットワーク

| ID | 要件 | 理由・実装メモ |
| --- | --- | --- |
| **F-1** | **`127.0.0.1` に明示的にバインドする。`0.0.0.0` / `::` にバインドしてはならない** | ループバック限定なら Windows Defender ファイアウォールの許可ダイアログが出ない。`0.0.0.0` にすると初回起動時にダイアログが出て、標準ユーザは許可できず詰む |
| **F-2** | **ポートは `0` を指定して OS に割り当てさせ、実際のポート番号を取得してから URL を組み立てる** | 固定ポートは衝突する。多重起動も自然に共存できる |
| **F-3** | **ワンタイムトークンを起動ごとに生成**（暗号論的乱数 128 bit 以上）し、URL に含めて渡す。トークンの無いリクエストは `401` で拒否する | 同一 PC の他プロセス・他ユーザからのアクセスを防ぐ。**ループバックであっても localhost は「同じ PC の誰でも叩ける」ことに注意** |
| **F-4** | **`Origin` および `Host` ヘッダを検証**し、ループバック以外を拒否する | 悪意ある Web ページからの **DNS リバインディング**攻撃を防ぐ。`Host` が `127.0.0.1:<port>` / `localhost:<port>` 以外なら拒否 |
| **F-5** | **`Access-Control-Allow-Origin: *` を設定しない**。CORS は許可しない | 外部サイトからの読み出しを防ぐ |

### F.2 プロセス寿命

| ID | 要件 | 実装メモ |
| --- | --- | --- |
| **F-6** | **ブラウザのタブを閉じたらサーバも終了すること** | ブラウザを閉じても子プロセスは死なない。次の 3 段構えにする: ①`pagehide` で `navigator.sendBeacon("/shutdown", token)` ②WebSocket の切断を検知 ③**最後の通信から 60 秒（設定可）無通信でプロセス終了**。①②は取りこぼしがあるため ③ が最終防衛線 |
| **F-7** | 起動から一定時間（例 15 秒）ブラウザが接続してこなければ、URL を標準出力に出して終了する | 既定ブラウザの起動に失敗した場合にプロセスが残らないようにする |

### F.3 起動と UI

| ID | 要件 | 実装メモ |
| --- | --- | --- |
| **F-8** | 既定ブラウザで自動的に URL を開く。失敗した場合は URL をコンソールに表示する | .NET なら `Process.Start(new ProcessStartInfo(url) { UseShellExecute = true })`。**既定ブラウザが IE の環境では動作しない**ため、その旨をメッセージに含める |
| F-9 | `--no-browser` / `--port <n>` / `--serve` などのオプションを持ち、CLI としても使えること | H-2 を選ぶ動機の一つ（§3.3 の条件 3）を実際に満たすため |
| F-10 | サーバはコンソールウィンドウを出さない（または最小化する）こと | 常時黒窓が残るのは体験が悪い。Windows では `OutputType=WinExe` にしてログはファイルへ |

### F.4 データ転送

`N = 1024` の PSF は `Float32Array` で 4 MB。**JSON にすると 10 倍以上に膨らむため、
必ずバイナリで送る。**

| ID | 要件 | 実装メモ |
| --- | --- | --- |
| F-11 | 配列は `Content-Type: application/octet-stream` の生バイナリ、または WebSocket のバイナリフレームで送る | ブラウザ側は `await res.arrayBuffer()` → `new Float32Array(buf)` |
| F-12 | 数値は **`float32` で送る**（内部計算は `float64`） | 表示用途では十分。転送量が半分になる |
| F-13 | スライダのドラッグ中は WebSocket を使い、**サーバ側で「最新のリクエスト以外を破棄」**する | HTTP のリクエスト・レスポンスを毎フレーム張るとキューが詰まる |
| F-14 | ドラッグ中は `N = 512`（1 MB）、確定時に `N = 1024` を送る | §8.2 の二段品質と整合させる |

### F.5 H-2 と H-3 の比較（判断材料）

| 観点 | H-2 (localhost サーバ) | H-3 (WebView2 埋め込み) |
| --- | --- | --- |
| ポート・ファイアウォール | 要対策（F-1〜F-5） | **不要**（IPC のみ） |
| プロセス寿命 | 要対策（F-6, F-7） | **ウィンドウを閉じれば終了** |
| ローカル露出 | 対策しないと他プロセスから叩ける | **なし** |
| 別 PC のブラウザから開く | **可能**（F-1 を緩める判断が要る） | 不可 |
| CLI/バッチとの同居 | **自然**（`--serve` を足すだけ） | 別バイナリか別モードが要る |
| ランタイム依存 | なし | WebView2 Runtime |
| UI の見た目 | 既定ブラウザ（タブ・アドレスバーが残る） | **単一ウィンドウでアプリらしい** |

**単一 PC で完結する用途なら H-3 の方が素直**である。H-2 は「別 PC から開きたい」
「CLI と同居させたい」という要件が実在する場合に選ぶこと。
